# 다음 긴급 배차를 위한 SORT 빈 차 공급 실험

`PACK → SORT`를 먼저 보내 하역 후 생긴 빈 차가 다음 긴급 픽업을 앞당기는지 확인했다. 일부 경우 SORT에 빈 차가 더 빨리 생겼지만, 다음 긴급 요청을 안정적으로 앞당기지 못했다. 과제에서 제출 가능한 후보도 기준 19대안보다 검증 비용이 높았다.

## 1. 배차 한 건을 바꿔 영향 측정

기존 19대·9노드 정책으로 기준 시뮬레이션을 실행했다. 워밍업 이후, SORT에 유휴 차량이 없고 PACK에서 SORT로 갈 요청이 기다리는 경우를 찾았다. 기준 정책은 SORT행이 아닌 일반 요청을 선택해야 하며, 선택한 차량이 공차 65m 이내에서 PACK에 갈 수 있어야 한다. SORT로 이미 가는 작업 차량이 있는지와 PACK까지 거리가 25m 이내인지에 따라 나눠, 시드와 그룹마다 최대 6건을 균등 표본으로 골랐다.

각 표본에서 같은 도착 목록으로 처음부터 재생하고, 동일 시각·차량·기존 요청·대체 요청을 확인한 뒤 **같은 차량의 한 번의 배차만** PACK → SORT로 바꿨다. 뒤따르는 배차는 모두 기존 정책이 처리했다. 시뮬레이터에서 하역 완료, 다음 신규 긴급 요청의 도착과 픽업, 원래 예정됐던 일반 요청의 픽업을 직접 기록했다.

| 조건 | 탐색 64시드에서 재생 | 새 128시드에서 재생 | 하역 완료 차이 | 다음 긴급 픽업 차이 | 원래 일반 요청 픽업 차이 |
|---|---:|---:|---:|---:|---:|
| 다른 SORT행 차량 없음 | 82건 | 164건 | +0.02분 | +0.09분 | +2.51분 |
| 다른 SORT행 차량 있음 | 384건 | 768건 | −0.40분 | −0.04분 | +2.86분 |

차이는 새 128시드에서 `한 건 변경 − 기준`을 시드별로 먼저 평균낸 값이다. 음수는 빨라졌다는 뜻이다. 다음 긴급 픽업 차이의 시드 단위 표준오차는 각각 0.07분, 0.03분이었다. 탐색 시드에서도 같은 두 그룹의 다음 긴급 픽업은 각각 +0.27분, +0.03분이었다. 조사한 조건에서 대체 차량의 공차 거리는 모두 25m였다.

다른 SORT행 차량이 없던 그룹에서 다음 긴급 요청은 개입 후 평균 **1.49분**에 들어왔고, 먼저 보낸 차량은 평균 **6.10분**에 SORT에서 하역을 마쳤다. 새 시드에서 이 차량이 직후 작업으로 다음 긴급 요청을 맡은 건은 두 그룹 합쳐 **31/932건**이었다. 10분간 새로 들어온 긴급 요청들의 요청당 대기 변화는 다른 SORT행 차량이 없을 때 +0.01분, 있을 때 −0.08분이었다. 이 보조 지표에서는 요청마다 대기를 최대 10분으로 잘라, 아직 픽업되지 않은 요청도 비교에 포함했다.

## 2. 허용된 CSV 규칙에서 후보 탐색

공식 트리는 목적지나 SORT에 들어오는 차량 수를 직접 볼 수 없다. PACK → SORT의 적재 거리는 90m이고 SHIP → RECV는 115m다. 이 때문에 `dl > 65`는 두 흐름을 함께 우선하고 `dl > 50`은 65m 흐름도 포함한다. `dl > 90`은 PACK → SORT가 빠지고 SHIP → RECV만 남으므로 음성 대조군으로 사용했다.

차량은 19대로 고정했다. 가까운 일반 요청을 처리하는 분기에서 적재 거리 우선 노드를 넣을 위치, `de`와 `qo` 임계값을 바꾸고 최대 9노드를 유지했다. PACK → SORT를 포함하는 후보 72개와 SHIP → RECV만 우선하는 대조 후보 36개를 분리해서 선별했다. 16개(16001–16016) → 64개(16001–16064) → 240개(17001–17240) 시드 순으로 평가하고, 마지막에 각 계열의 후보 CSV를 고정했다.

| 후보 | 240시드 차이 | 신규 3,600시드 차이 ± 표준오차 | 실격 |
|---|---:|---:|---:|
| PACK → SORT를 포함하는 최선안 | +4.35 | **+5.64 ± 0.22** | 0/3,600 |
| SHIP → RECV만 우선하는 음성 대조안 | +0.28 | +0.97 ± 0.20 | 0/3,600 |

차이는 각 시나리오의 후보 비용에서 같은 시나리오의 기준 비용을 뺀 값이다. 단위는 천원/시간이다. 최종 시드 범위는 PACK 포함안 22001–25600, 음성 대조안 18001–21600이다. PACK 포함안의 3,600시드 평균은 1,196.95, 같은 시드의 19대 기준안은 1,191.31이었다.

PACK 포함안은 근거리 적체 기준도 바꾸고 원거리 긴급 노드 하나를 제거했다. 이 변화들을 따로 보려고, 후보에서 **추가한 `dl > 50` 노드만 제거한 8노드 대조안**을 같은 3,600개 시드에서 평가했다. 거리 규칙을 추가하자 긴급 P95는 0.009분 줄었지만 평균 픽업 대기는 0.018분 늘었고, 총비용은 **1.02 ± 0.23점 증가**했다. 따라서 후보 전체의 5.64점 열세 중 거리 규칙 자체가 낸 효과를 따로 확인할 수 있다.

## 3. 왜 기준안을 유지하는가

이 실험은 기존 트리 주변의 모든 정책을 열거하거나 전역 최적을 증명하지 않는다. 대신, 다음 두 판단을 뒷받침한다.

- 기존 정책에서 한 건을 앞당기는 효과는 조건마다 달랐다. 새 시드에서 다른 SORT행 차량이 있을 때 하역 완료 시각은 앞당겨졌지만, 다음 긴급 픽업의 변화는 작았다. 원래 선택된 일반 요청의 픽업 대기는 두 그룹에서 모두 늘었다.
- 공식 CSV로는 목적지나 들어오는 차량의 하역 예정 시각을 직접 판단할 수 없다. 시험한 거리 규칙은 여러 흐름을 함께 우선했고, 이를 반복 적용한 후보는 같은 요청 목록에서 더 비쌌다. **흐름을 직접 알아보는 진단 실험과 공식 규칙의 성능을 따로 해석해야 한다.**

`answer_final_best.csv`는 현 제출안으로 유지한다.

## 4. 파이프라인 코드와 재현

[agv_opt.cpp](../../agv_opt.cpp)는 선택한 배차와 하역 완료를 기록하며, [agv_sort_supply.hpp](../../agv_sort_supply.hpp)가 한 건 재생과 제출 형식 후보 탐색을 제공한다. [요약 스크립트](sort_replay_summary.py)는 같은 시드 내에서 여러 배차를 바꿔 재생한 경우를 먼저 묶어 평균과 표준오차를 계산한다.

Visual Studio 개발자 PowerShell에서 저장소 루트를 작업 디렉터리로 두고 실행한다. 새 출력 파일명을 사용한다.

```powershell
cl /nologo /std:c++20 /O2 /EHsc /utf-8 agv_opt.cpp /Fe:agv_opt.exe
.\agv_opt.exe --verify answer_final_best.csv
.\agv_opt.exe --yb-sort-replay answer_final_best.csv sort_discovery.csv 14001 64
.\agv_opt.exe --yb-sort-replay answer_final_best.csv sort_confirmation.csv 15001 128
python experiments/younbean/sort_replay_summary.py sort_discovery.csv sort_confirmation.csv
.\agv_opt.exe --yb-sort-search answer_final_best.csv sort_reproduced.csv
.\agv_opt.exe --yb-audit answer_final_best.csv experiments/younbean/sort_candidate.csv 22001
.\agv_opt.exe --yb-audit answer_final_best.csv experiments/younbean/sort_negative_control.csv 18001
.\agv_opt.exe --yb-audit experiments/younbean/sort_matched_control.csv experiments/younbean/sort_candidate.csv 22001
```

기준안의 800시드 평균 1,191.27점을 재현했다. 기준안, 두 후보와 8노드 대조안은 각각 15개 시드에서 빠른 평가와 전수 배차 쌍 평가의 비용 차이가 0이었다.
